# 注释与文档规范

> 触发条件：新增或修改 `.c`、`.h`、驱动接口、模块说明、公共 API、硬件约束或重要业务逻辑时，必须先阅读本文件。

注释用于补充代码无法直接表达的工程事实、硬件约束和设计意图。新增或修改 MCU C 业务代码注释时，格式统一采用中文结构化注释风格。

## 语言规则

- 交互与规则文档使用简体中文。
- 代码注释默认使用简体中文；MCU C 业务代码使用中文结构化注释格式；若当前文件是厂商、第三方或工具生成文件，优先匹配当前文件风格。
- 自动生成文件不主动补充大段注释，避免影响后续重新生成。
- 中文源码与文档保持 UTF-8 编码。

## 统一注释格式

- 函数、公共接口、模块说明和重要内部函数的块注释使用以下中文结构化格式：

```c
/**
 ******************************************************************************
  @功能：说明函数或接口的职责
  @日期：YYYY-MM-DD
  @参数：[输入] xxx - 参数说明
  @返回值：类型 - 返回语义和失败含义
  @使用说明：调用时机、调度要求、硬件或并发注意事项
 ******************************************************************************
 */
```

- 无参数或无返回值写 `无`；多参数按行续写并说明 `[输入]`、`[输出]` 或 `[输入输出]`。
- `@功能`、`@日期`、`@参数`、`@返回值` 是函数/接口块注释的默认字段；按需增加 `@使用说明`、`@线程安全`、`@引脚连接`、`@注意` 等项目已有字段。
- 模块分区使用 `/* ======================== 模块名 ======================== */`。
- 结构体字段、设备表、宏配置和关键状态位使用简短中文行内注释，例如 `field; /* 含义 */`。
- ESP8266/Arduino 单文件工程可沿用项目里的 `@函数`、`@功能` 和 `/******************************************************************************* ... */` 区域分隔格式。
- CubeMX、厂商 SDK、CMSIS、HAL、FreeRTOS 和第三方库文件保持原有英文/Doxygen 风格；只在允许的 `USER CODE` 区或业务扩展文件中使用中文结构化格式。

## 什么时候需要注释

- 公共接口的调用前置条件、返回语义、所有权或失败处理不明显。
- 硬件连接、复用冲突、电平有效性、时序边界或资源限制会影响移植。
- 中断、DMA、缓冲区、状态机和主循环之间存在并发或生命周期约束。
- 参数来源来自标定、实测、协议约定或安全边界，需要让维护者知道依据。
- 临时兼容旧硬件、旧协议或旧 SDK 的逻辑无法通过命名清楚表达。

## 什么时候不写注释

- 函数名、变量名和类型已经清楚表达行为。
- 注释只是在复述代码做了什么。
- 不为作者、变更历史等无助于当前维护的信息额外写注释；业务函数/接口块注释按统一格式保留 `@日期`。
- 在多个文件重复同一份说明；应把说明放在最接近真实约束的接口或模块处。

## 接口说明原则

- 公共头文件说明“调用者必须知道什么”，源文件内部说明“维护者必须小心什么”。
- 硬件驱动接口应说明依赖的外设资源、初始化前置条件、是否可在中断中调用、缓冲区所有权和错误返回语义。
- 协议接口应说明帧边界、最大长度、超时、重试、字段校验和兼容范围。
- 控制算法接口应说明输入单位、取值范围、更新频率和异常输入处理。

## 禁止事项

- 禁止在业务 C 代码中混用随意的英文 `@brief/@param` 模板，除非当前文件本身是厂商、第三方或工具生成风格。
- 禁止在厂商生成文件或第三方库里强行改成中文结构化格式。
- 禁止脱离当前实现复制旧注释内容，或保留错误的日期、参数、返回值和硬件说明。
- 禁止把示例项目的传感器、引脚、协议字段写成跨项目通用注释要求。
- 禁止用注释掩盖不清晰的命名、过长函数或混乱职责。

## 完成检查清单

- 注释是否解释了代码本身看不出的约束。
- 注释是否随着当前实现保持一致。
- 公共接口是否包含必要的调用边界和失败语义。
- 自动生成文件和厂商文件是否保持原有风格。
