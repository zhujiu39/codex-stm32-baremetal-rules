# 交付逻辑规范

> 触发条件：涉及固件、源码、配置、外部资源、烧录文件、交付包、生产包、调试版/正式版切换，或用户要求“每次改动都重新做交付包”时，必须先阅读本文件。

本文件约束交付动作和交付包结构。交付不是简单复制一个 `.hex` 或 `.bin`，而是把本次真实改动、验证结果、烧录资源和可追溯说明打成一个独立、不会和旧版本混淆的目录。

## 基本原则

- 每次发生代码、资源、构建配置或交付内容变更后，都必须重新生成一个新的交付目录。
- 不复用、不覆盖旧交付目录；旧交付目录只能作为历史证据，不能当成本次交付。
- 交付目录名必须包含时间、版本前缀和本次改动内容，推荐格式：`yyyyMMdd_HHmmss_版本前缀_本次改动内容`。
- 若用户指定固定交付根目录，必须始终放到该目录下；没有指定时，优先使用当前项目内已有的 `交付文件`、`生产交付` 或同类目录。
- 交付目录名必须和实际内容一致；正式、调试、功能测试、工厂固件不能混用名字。
- 交付前必须用项目真实构建方式重新构建，例如 Keil 工程必须使用 Keil/UV4，而不是手工拼出一个看似可用的文件。
- 交付说明必须写清楚本次改了什么、怎么验证、烧录哪个文件、烧录到哪里、还有哪些限制或注意事项。

## 交付目录结构

按项目实际情况选择目录，但语义必须清楚。推荐结构：

```text
交付文件/
└── yyyyMMdd_HHmmss_版本前缀_本次改动内容/
    ├── 交付说明.md
    ├── SHA256SUMS.txt
    ├── 固件/
    ├── W25Q16资源/
    ├── 源码变更/
    └── 文档/
```

- `固件/`：放 MCU 可烧录或可排查的构建产物。
- `W25Q16资源/`：放外部 Flash、字库、图片包、资源清单、资源说明。
- `源码变更/`：放本次涉及的关键源码快照，不把整个工程无差别复制进去。
- `文档/`：放需求、说明、表格、测试记录等非固件材料。
- `SHA256SUMS.txt`：记录交付目录内关键文件的 SHA256，便于确认用户烧录和拿到的是同一份文件。

目录可以按项目裁剪，但不能缺少本次交付所需的核心材料。

## 固件交付内容

固件类交付优先包含：

- 可烧录文件：`.hex`、`.bin` 或项目指定格式。
- 可排查文件：`.axf`、`.elf`、`.map`、反汇编或符号文本，按项目需要选择。
- 构建日志：必须是本次新构建产生的日志，不能拿历史日志充数。
- 构建配置来源：例如 `.uvprojx`、`.ioc`、CMake 配置或关键工程文件；若工程文件没有变化，可以不复制，但交付说明要写明构建入口。

Keil 工程交付时必须检查日志中的最终结果，例如：

```text
0 Error(s), 0 Warning(s)
```

如果有 warning 或 after-build 失败，不能包装成无问题交付；必须在交付说明中写清楚 warning/失败是否影响烧录文件，以及最终采用的产物来源。

## 外部资源交付内容

涉及 W25Q16、SPI Flash、字库、图片包、音频包或其他外部资源时，必须和 MCU 固件一起交付匹配资源。

资源交付优先包含：

- 推荐烧录文件，例如 `*_pack_64k.bin` 或项目指定的完整镜像。
- 实际长度资源包，例如 `*_pack.bin`。
- 资源清单，例如 `manifest.csv`、`manifest.json`。
- 固件使用的资源地址头文件或等价定义，例如 `*_image_table.h`。
- 资源说明，必须写清推荐烧录地址、包头格式、资源偏移和注意事项。

外部资源必须做基本一致性校验：

- 固件检查的 magic 与资源包实际开头一致。
- 固件宏定义的偏移、长度、宽高、帧数与 manifest 一致。
- 每个资源的长度不越界。
- manifest 中记录的 CRC 与资源包实际数据一致。
- 填充版镜像长度符合预期，前缀等于实际资源包，尾部填充值符合说明。

如果资源包仍包含调试期文件，但正式固件不再使用，正式交付包不要把调试资源混进去，避免用户烧错。

## 交付说明要求

每个交付目录必须有 `交付说明.md`，至少包含：

- 交付时间。
- 本次修改摘要。
- 编译方式和编译结果。
- 固件文件列表。
- 外部资源文件列表。
- 烧录说明：MCU 烧录哪个文件，外部 Flash 烧录哪个文件，烧录地址是什么。
- 验证结果：构建日志结果、资源校验结果、必要时包含文件大小和 SHA256。
- 已知限制：未上板验证、硬件条件依赖、需要用户确认的内容等。

交付说明不能只写“已完成”；必须让用户不用翻代码也知道该烧什么、怎么烧、这版和上一版差异是什么。

## 版本与命名

- 目前只使用四类版本前缀：`release_`、`debug_`、`test_`、`factory_`。
- 正式固件使用 `release_` 前缀，用于现场、客户、正常功能验收或生产默认烧录，例如 `release_CAN_NormalMode_Receive.hex`。
- 调试固件使用 `debug_` 前缀，用于显示调试页、原始数据、错误计数、日志标记或临时诊断，例如 `debug_CAN_raw_rx.hex`。
- 功能测试固件使用 `test_` 前缀，用于单项功能验证、局部硬件验证或短期试验，例如 `test_led_sink_current.hex`。
- 工厂固件使用 `factory_` 前缀，用于产线、老化、IO 自检、出厂检测或工装流程，例如 `factory_io_selftest.hex`。
- 同一个交付目录里如果同时放正式固件和调试固件，文件名必须用前缀区分，不能只靠目录名或交付说明区分。
- 外部资源文件也必须按用途加前缀；正式 UI 资源用 `release_`，调试页专用字库或图片用 `debug_`，工厂测试资源用 `factory_`。
- 修复类目录名必须在版本前缀后写出修复对象，例如 `20260706_143000_release_CAN多帧解析接收修复`。
- 如果用户指出交付逻辑错误或漏交付，下一次交付必须新建目录，并在说明里写清修正点。

## 完成前检查

- 是否重新构建了本次代码，而不是复用旧产物。
- 是否确认输出文件时间、大小和日志都来自本次构建。
- 是否把 MCU 固件和外部资源同时交付，且二者版本匹配。
- 是否删除或排除了本次不再使用的调试资源。
- 是否创建了新的“时间+版本前缀+内容”交付目录。
- 是否给交付固件和外部资源文件使用了 `release_`、`debug_`、`test_` 或 `factory_` 前缀。
- 是否写了 `交付说明.md` 和 `SHA256SUMS.txt`。
- 是否明确告诉用户交付路径、推荐烧录文件和烧录地址。
